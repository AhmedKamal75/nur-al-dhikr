### UP-01 — Qur'an Word Study Popup 2.0 (the single biggest depth delta vs Ayah / Muslim Pro / Qalbox)

**Current (verified):** tap-to-open on every word in reader + mushaf (`tafsirPanel.js:51-83`, `handlers/quran.js:221-244`). Popup already shows: word text, transliteration, EN gloss, grammar summary (POS · verb Form I–X · case/mood — `wordStudy.js:53-69`), detail tags (PGN, definiteness, naʿt, passive, sarf pattern `:94-106`), affix glosses (`:109-114`), **root + Qur'an-wide count + 8 occurrence chips + "Browse all N"** (`tafsirPanel.js:261-289`), **per-word tajweed inspector** (rule EN/AR + description + colored letters, same classifier as the page, `:108-207`), and a "Tafsir & Iʿrab" deep-link CTA (`:240-244`). Graceful tajweed-only fallback when word data is absent (`:220-246`). Surface-anchored resolution survives spelling-split ayahs (`wordStudy.js:19-46`). Data: Quranic Arabic Corpus morphology + quranwbw gloss, documented in `data/SOURCES.md:10-29`; per-surah lazy tier `lazyData.js:303-323`.
**Gap:** no Arabic gloss (`occurrenceGloss` returns `''` for `ar` by design, `roots.js:185-188`); no synonyms/antonyms; **no per-word audio**; no per-word copy/share/bookmark; no bridge into mutashabihat; tajweed inspector exists but has no "hear it" affordance.
**Rich spec:**

- _Data:_ new immutable `data/quran-dict.json` (lemma → `{syn:[], ant:[], arGloss:{en,ar}, freq}`; ~300 KB, SW-precached, bilingual fields per parity rule #4) + optional `lemma` field on existing `data/quran-words/{n}.json` records (same corpus lineage → integrity tests per constraint §3).

### UP-02 — Settings deep-link arrival: smooth-scroll the target section to top + move focus (the mandated navigation check)

**Current (verified):** `#/settings/<slug>` plumbing is 90% built — slug validation both directions (`settings.js:44-62`), persisted pin via `settingsSection` (`stateSub.js:121-134`), target `<details>` rendered open (`settings.js:208-217`), scroll _restore_ on Back works (`renderer.js:665-674`). But **nothing ever scrolls on arrival**: grep for `scrollIntoView|scrollTo` across `stateSub.js / views/settings.js / handlers/system.js` = **zero hits**; the renderer _forces_ `mainEl.scrollTo(top:0)` on view change (`renderer.js:677-681`), so a palette/deep-link jump lands at the very top with the chosen section expanded somewhere below the fold. The CSS half of the contract is dead code — `scroll-margin-top: calc(var(--topbar-height) + var(--space-4))` (`components.css:285-287`) only fires on a scrollIntoView/fragment that never happens. Same-view slug→slug changes are worse: `viewChanging === false` → no scroll reset **and no focus move** at all (`renderer.js:615,695` are view-change-gated). The exact pattern already exists in-repo — `handlers/worship.js:47-57` (`calendar-goto-fasting`) does `scrollIntoView({behavior: scrollBehavior(), block:'start'})` — it was just never applied to settings.
**Rich spec:** after the NAVIGATE render _and_ after same-view slug changes (gate on "slug param present" so Back's restored offset isn't fought): rAF → `document.getElementById(openSettingsSectionFor(state))?.scrollIntoView({ behavior: scrollBehavior() /* utils.js:197-209 — returns 'auto' under reduced motion */, block:'start' })`, then `summary.focus({ preventScroll: true })` (summaries are natively focusable) so SRs announce the section instead of only `#main` (`renderer.js:695`). Existing `scroll-margin-top` handles the 64px sticky topbar; nothing new to add to CSS.
**Acceptance:** palette → "Data" lands with the Data section header at viewport top (accounting for topbar), focus on its summary, reduced-motion users get an instant jump, Back still restores the previous scroll position, accordion memory still persists. **Effort: S (~15 lines + test).** Regression: e2e `#/settings/data` → section top within 1 viewport of `scrollTop ≈ section.offsetTop − topbarHeight`.
